# System of Record на YDB
![Архитектурная схема](architecture.svg)

## Назначение

Архитектура хранит каноническое состояние домена в строковых таблицах YDB. Единственный источник истины — `Entities` и `Relations`; топик изменений, кэши и представления downstream-систем восстанавливаются из них и не принимают доменные решения вместо API.

## Когда применять

- Для мастер-данных, профилей, каталогов и других доменов, где требуется строгая транзакционная запись.
- Когда несколько получателей должны независимо реагировать на подтвержденные изменения.
- Когда аудит и повтор запроса должны быть частью одной ACID-транзакции.

## Компоненты

- **API / доменный сервис** проверяет команды и выполняет транзакции.
- Строковые таблицы YDB: `Entities(entity_id, ...)`, `Relations(source_id, relation_type, target_id, ...)`, `IdempotencyKeys(scope, key, ...)`, `AuditLog(entity_id, version, ...)`.
- **CDC changefeed** для `Entities` и `Relations` exactly-once записывает каждую change record во внутренний changefeed topic соответствующей таблицы. Порядок сохраняется для изменений одного полного первичного ключа. YDB Topics — журнал pub/sub: у каждого consumer group своя позиция чтения.
- Downstream consumers: индексатор поиска, обновление кэша и интеграционный обработчик.
- **Coordination Service** выбирает единственного исполнителя фонового обслуживания: очистки истекших ключей и проверки целостности.

## Основной поток

1. Клиент отправляет команду с `idempotency_key` в API.
2. Сервис читает `IdempotencyKeys`; повтор возвращает ранее сохраненный результат.
3. В одной ACID-транзакции сервис изменяет `Entities` и `Relations`, добавляет запись в `AuditLog` и фиксирует ключ в `IdempotencyKeys`.
4. После commit CDC exactly-once помещает change records во внутренние changefeed topics `Entities/entity-changes` и `Relations/relation-changes`.
5. Независимые consumer groups читают журнал, идемпотентно обновляют свои проекции и подтверждают смещение.
6. Чтение актуального состояния выполняется из строковых таблиц через API; производные представления допустимы только для ослабленно согласованных сценариев.

## Согласованность и надежность

Граница атомарности — одна транзакция YDB над строковыми таблицами. CDC exactly-once записывает change record подтвержденного изменения во внутренний changefeed topic и сохраняет порядок для одного полного первичного ключа. После сбоя чтение с последнего подтвержденного offset и обработка consumer могут повториться, поэтому потребитель применяет запись идемпотентно по полному ключу, версии и метаданным изменения. Глобальный порядок между разными ключами не предполагается.

Coordination Service не заменяет ACID-транзакции и не защищает доменные инварианты. Любой внешний side effect — HTTP-вызов, письмо или изменение внешней системы — требует идемпотентности и не считается атомарным с commit в YDB.

## Масштабирование и ключи партиционирования

`Entities` распределяется по равномерному `entity_id`; монотонный timestamp не должен быть первым ключом. Для `Relations` ключ начинается с хэшированного `source_id`, затем содержит `relation_type` и `target_id`. `IdempotencyKeys` использует `(scope_hash, key)`, а `AuditLog` — `(entity_hash, version)`. Changefeed партиционируется по полному первичному ключу исходной таблицы: для `Entities` это `entity_id`, для `Relations` — весь составной ключ. API и consumers масштабируются горизонтально.

## Отказы и восстановление

При неопределенном результате commit клиент повторяет запрос с тем же ключом. Consumer после сбоя продолжает с подтвержденного смещения и безопасно переигрывает событие. Отставание групп и ошибки changefeed должны наблюдаться отдельно. Потерянная downstream-проекция пересобирается из таблиц или повторным чтением журнала в пределах retention. Singleton maintenance возобновляется новым владельцем lease Coordination Service; операции обслуживания обязаны быть повторяемыми.

## Ограничения и антипаттерны

- Нельзя считать топик, кэш или поисковый индекс источником истины.
- Нельзя публиковать событие до commit или выполнять внешний side effect внутри расчета на «общую транзакцию».
- Нельзя использовать Coordination Service как распределенную замену проверкам версий и ACID.
- Нельзя создавать горячую партицию монотонными ключами или одной группой для всех сущностей.
- Архитектура описывает только строковые таблицы и транзакционные нагрузки.
