# CQRS с CDC и версионируемыми проекциями
![Архитектурная схема](architecture.svg)

## Назначение
CQRS разделяет модель записи и модели чтения. Внешний по отношению к границе YDB обработчик команд атомарно изменяет нормализованную модель записи и добавляет доменные записи в таблицу `OrderEvents` только на добавление; CDC этой единственной таблицы создает ровно одну запись об изменении на зафиксированное изменение строки в `order-events.changefeed`. Внешние приложения-проекторы строят денормализованные строковые модели чтения для внешнего Query API. YDB Topics здесь — воспроизводимый журнал pub/sub с именованными YDB Consumers, а не очередь конкурирующих потребителей (competing consumers).

## Когда применять
- Профиль записи и набор запросов существенно различаются.
- Для чтения нужны несколько представлений с независимым масштабированием и жизненным циклом.
- Допустима явно измеряемая согласованность в конечном счёте между подтверждением команды и появлением данных в Query API.
- Нужны безопасная пересборка и переключение версии проекции без остановки записи.

## Компоненты
- **Command API / обработчик**: принимает `command_id`, проверяет бизнес-инварианты и выполняет ACID-транзакцию.
- **Модель записи**: нормализованные строковые таблицы `Orders` (`order_id`), `OrderLines` (`order_id`, `line_no`) и результаты идемпотентных команд `CommandResults` (`command_id`).
- **Источник CDC**: строковая таблица `OrderEvents` только на добавление с полным первичным ключом (`order_id`, `event_seq`). Этот PK задает идентичность записи и порядок событий одного заказа; `customer_id` для `OrdersByCustomer_v1` хранится в полезной нагрузке события.
- **CDC / поток изменений (changefeed)**: `order-events.changefeed` принадлежит только `OrderEvents` и создает ровно одну запись об изменении на зафиксированное изменение строки. Это внутренний CDC Topic: ему нельзя назначать произвольные `producer_id`/`message_group_id`. Чтение и обработка подписчиком могут повториться.
- **Проекторы вне YDB**: приложения используют именованные `YDB Consumer orders-summary-v1`, `YDB Consumer orders-by-customer-v1` и временный `YDB Consumer orders-summary-v2-rebuild`.
- **Модели чтения**: строковые таблицы `OrderSummary_v1` (`order_id`), `OrdersByCustomer_v1` (`customer_id`, `updated_bucket`, `order_id`) и новая `OrderSummary_v2`.
- **Прогресс и дедупликация**: встроенное смещение (offset) consumer YDB Topic фиксируется транзакционно вместе с моделью чтения. `ProjectionOffsets` (`projection_name`, `partition_id`) хранит версию проектора и диагностическое отставание, но не служит вторым смещением возобновления; `ProcessedEvents` имеет ключ (`projection_name`, `source`, `order_id`, `event_seq`), где `source = OrderEvents`.
- **Query API вне YDB**: читает только активную версию модели чтения; указатель хранится в `ProjectionRegistry` (`projection_name`).
- **Coordination**: аренда (lease) обработчика пересборки и сериализация переключения версии; Coordination не заменяет ACID.

## Основной поток
1. Клиент отправляет команду с `command_id` в Command API.
2. Обработчик читает нужную версию модели записи, проверяет инварианты и в одной YDB ACID-транзакции изменяет `Orders`/`OrderLines`, добавляет одну или несколько строк в `OrderEvents` с последовательными `event_seq` и сохраняет результат в `CommandResults`; повтор `command_id` возвращает тот же результат.
3. CDC, привязанный только к `OrderEvents`, создает ровно одну запись об изменении на зафиксированное изменение строки в `order-events.changefeed`. Идентичность события — (`source = OrderEvents`, `order_id`, `event_seq`); дополнительный случайный идентификатор не вводится.
4. Каждый внешний проектор читает `order-events.changefeed` через свой именованный YDB Consumer. В одной совместной транзакции Topic и таблиц YDB он изменяет строковую модель чтения и `ProcessedEvents`, затем транзакционно фиксирует встроенное смещение consumer соответствующих партиций. При откате не фиксируются ни модель, ни смещение; повтор чтения безопасен.
5. Query API читает активную таблицу, указанную в `ProjectionRegistry`; сразу после шага 2 старая версия ответа еще допустима — это согласованность в конечном счёте.
6. Для пересборки создаются новая строковая модель чтения `OrderSummary_v2` и отдельный `YDB Consumer orders-summary-v2-rebuild`. Согласованная опорная точка таблицы `OrderEvents` только на добавление привязывается к позиции `order-events.changefeed`, после чего этот consumer догоняет оперативный поток до контрольного встроенного смещения.
7. После проверки полноты и отставания `ProjectionRegistry` атомарно переключает Query API с `OrderSummary_v1` на `OrderSummary_v2`; v1 сохраняется для быстрого отката и удаляется позже по регламенту.
8. Любые внешние эффекты проектор выполняет идемпотентно по (`source`, `order_id`, `event_seq`); предпочтительно отделять их от построения проекции.

## Согласованность и надежность
На схеме подписи краткие: проектор фиксирует модель чтения, ProcessedEvents и смещение consumer одной совместной транзакцией Topic и таблиц (см. основной поток).
Модель записи и добавление в `OrderEvents` согласованы одной ACID-транзакцией, модели чтения — согласованность в конечном счёте. CDC создает ровно одну запись об изменении на зафиксированное изменение строки; именованный YDB Consumer может повторно прочитать или начать обработку записи после сбоя. Совместная транзакция Topic и таблиц атомарно фиксирует изменение модели чтения и встроенное смещение по партициям, а идентичность (`source`, `order_id`, `event_seq`) защищает повторное воспроизведение. Внешние эффекты идемпотентны по этой идентичности. Coordination управляет владением работой, но не обеспечивает атомарность таблиц.

## Масштабирование и ключи партиционирования
В `OrderEvents` полный PK (`order_id`, `event_seq`) задает идентичность и последовательность событий заказа; внутренний поток изменений наследует источник и не получает пользовательские идентификаторы писателя. Один чрезмерно горячий `order_id` требует пересмотра границы агрегата. `OrdersByCustomer_v1` распределяет крупных клиентов дополнительным `updated_bucket`; если bucket вычисляется hash-функцией, полный PK обязательно сохраняет исходные `customer_id` и `order_id`, а не идентичность только по хешу. Встроенное смещение consumer ведется отдельно по партициям именованного YDB Consumer; `ProjectionOffsets` не участвует в протоколе возобновления.

## Отказы и восстановление
- При падении проектор продолжает со встроенного смещения по партициям своего именованного YDB Consumer. Незафиксированный пакет читается снова; совместная транзакция Topic и таблиц не оставляет частично обновленную модель чтения.
- «Ядовитое» событие с идентичностью (`OrderEvents`, `order_id`, `event_seq`) переводит конкретную проекцию в состояние `blocked`, сохраняется с диагностикой и исправляется контролируемым повторным воспроизведением; тихо пропускать событие нельзя.
- При длительном простое выполняется пересборка новой версии из `OrderEvents` и `order-events.changefeed`, а не изменение активной таблицы на месте.
- Если v2 не догнала контрольное смещение или не прошла сверку, переключение не выполняется; активной остается v1.
- Неопределенный результат команды повторяется с тем же `command_id`; внешние вызовы — только с идемпотентным ключом.

## Ограничения и антипаттерны
- Нельзя писать через Query API или изменять модель чтения вручную как источник истины.
- Нельзя фиксировать встроенное смещение consumer отдельно от транзакционного обновления проекции; `ProjectionOffsets` нельзя использовать как конкурирующий механизм возобновления.
- Нельзя обещать мгновенную согласованность после команды без отдельного протокола чтения своих записей.
- Нельзя перестраивать активную таблицу на месте: используйте новую версию и атомарное переключение.
- Нельзя объединять изменения разных исходных таблиц в один поток изменений или назначать внутреннему CDC Topic пользовательские `producer_id`/`message_group_id`: `order-events.changefeed` принадлежит только `OrderEvents`.
- Нельзя вводить дополнительный случайный идентификатор вместо естественной идентичности (`source`, `order_id`, `event_seq`).
- Нельзя считать Coordination заменой ACID, Topic — очередью конкурирующих потребителей, а срок хранения topic — бессрочным архивом данных.
