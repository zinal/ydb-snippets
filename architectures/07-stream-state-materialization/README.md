# Потоковая материализация операционного состояния в YDB

![Архитектурная схема](architecture.svg)

## Назначение

Архитектура поддерживает актуальное операционное состояние сущностей по потоку событий: последнее состояние, счетчики и активные предупреждения. Это не аналитическое хранилище и не замена DWH/OLAP: материализации рассчитаны на точечные и короткие диапазонные запросы к строковым таблицам YDB.

## Когда применять

- события приходят непрерывно, а приложению нужен быстро читаемый актуальный срез;
- порядок важен внутри одной сущности, но не требуется глобальный порядок;
- результат обработки события можно атомарно зафиксировать вместе с прогрессом consumer group;
- допустима доставка «как минимум один раз» за пределами локальной транзакции при наличии идемпотентности.

Для простой stateless-трансформации с последующим UPSERT допустим опциональный Transfer. Оконные вычисления, сложные переходы состояния, несколько взаимозависимых записей и бизнес-валидация должны выполняться приложением-процессором.

## Компоненты

| Компонент | Роль |
|---|---|
| Producers | Публикуют события с `entity_id` как ключом партиционирования |
| Input Topic | YDB Topics: долговечный pub/sub log с партициями, offset и независимыми consumer groups |
| Processor group | Экземпляры приложения используют встроенное транзакционное чтение Topic и материализуют состояние |
| CurrentState | Строковая таблица актуального состояния, ключ `entity_id` |
| Counters | Строковая таблица операционных счетчиков; ключ включает `entity_id` и тип счетчика |
| Alerts | Строковая таблица активных предупреждений; ключ начинается с `entity_id` |
| Downstream Topic | YDB Topics pub/sub log для производных событий |
| CDC changefeed | Асинхронный поток изменений строковых таблиц для подписчиков |
| Transfer (опционально) | Только stateless-преобразование и UPSERT без сложной бизнес-логики |

Yandex Message Queue здесь не требуется. YMQ — отдельная SQS-совместимая очередь поверх YDB для competing consumers, visibility timeout, retry и DLQ; она не является YDB Topic и не предоставляет модель pub/sub log с offset consumer group.

## Основной поток

1. Producer публикует событие в Input Topic с ключом `entity_id`.
2. Topic направляет все события одной сущности в одну партицию, сохраняя их порядок в пределах этой партиции.
3. Экземпляр processor group начинает встроенную транзакцию чтения YDB Topic и получает очередное событие вместе с позицией consumer group.
4. В этой же ACID-транзакции YDB процессор изменяет `CurrentState`, `Counters` и/или `Alerts` и выполняет transactional commit consumer offset средствами Topic API. Конкурирующая прикладная таблица offset не используется.
5. После commit новые значения синхронно доступны операционным запросам.
6. Производные события асинхронно попадают в Downstream Topic через надежно сохраняемый выход либо изменения таблиц публикуются CDC changefeed.
7. CDC exactly-once записывает change record для зафиксированного изменения. Подписчик может обработать этот record повторно и поэтому ведет собственный прогресс и остается идемпотентным.

## Согласованность и надежность

Изменение материализаций и встроенный transactional commit consumer offset атомарны, потому что выполняются в одной транзакции YDB. При повторе до commit транзакция снова читает событие; после успешного commit Topic начинает со следующей позиции. Commit дает строгую согласованность строковых таблиц; downstream Topic и CDC остаются асинхронными. Гарантия CDC exactly-once относится к созданию change record, а не к единственному выполнению кода подписчика.

Публикация во внешний сервис не входит в ACID-транзакцию YDB. Такой side effect обязан быть идемпотентным, например по `event_id`. Coordination не заменяет ACID и не делает совокупность записи, публикации и внешнего вызова единой транзакцией.

## Масштабирование и ключи партиционирования

Ключ Topic — `entity_id`: он сохраняет порядок событий сущности и распределяет разные сущности по партициям. Число активных процессоров ограничено числом партиций Topic. Ключи строковых таблиц начинаются с хорошо распределенного `entity_id`; монотонное время не следует ставить первым компонентом ключа. Для «горячих» сущностей нужна осознанная декомпозиция, поскольку произвольное шардирование одной сущности разрушает ее порядок.

## Отказы и восстановление

До commit событие может быть прочитано повторно, но изменения row tables и consumer offset откатятся вместе. После commit процессор возобновляет чтение со следующего offset. Недоступный downstream не должен блокировать уже зафиксированное состояние: публикация повторяется из надежно сохраненного выхода либо восстанавливается по CDC. CDC не дублирует change record для одного изменения, однако subscriber processing может повториться после сбоя. Отставание consumer group и CDC контролируется по lag; исчерпание retention до восстановления требует переигрывания из резервного источника или перестроения материализации.

## Ограничения и антипаттерны

- Использовать материализацию как аналитическое хранилище или выполнять широкие сканы.
- Считать порядок глобальным, хотя Topic гарантирует его только внутри партиции.
- Менять таблицы и фиксировать offset раздельно либо дублировать встроенный offset конкурирующей прикладной таблицей.
- Выполнять сложную stateful-логику в Transfer.
- Вызывать внешний API внутри повторяемого обработчика без idempotency key.
- Считать Coordination заменой транзакции или путать Topics с YMQ.
