# Надежные фоновые задания с YDB и SQS

![Архитектурная схема](architecture.svg)

## Назначение

Архитектура отделяет прием бизнес-запроса от длительной фоновой работы. Producer атомарно изменяет бизнес-данные и создает задание с записью Outbox; диспетчер доставляет его во встроенную очередь SQS YDB, а конкурирующие обработчики выполняют работу с повторами, дедупликацией и контролируемым завершением.

## Когда применять

- обработка дольше допустимого времени синхронного ответа;
- нагрузку нужно сглаживать очередью и независимо масштабировать обработчиков;
- требуются visibility timeout, повтор/экспоненциальная задержка, DLQ и ручной повтор;
- бизнес-транзакция должна надежно порождать задание без окна двойной записи.

Если нескольким независимым подписчикам нужен журнал событий, применяется YDB Topic. Если одно задание должен забрать один из конкурирующих потребителей (competing consumers), применяется встроенная очередь SQS.

## Компоненты

| Компонент | Роль |
|---|---|
| Producer / API | Внешнее приложение: в одной транзакции меняет бизнес-таблицы и регистрирует задание |
| Business tables | Строковые таблицы предметной области |
| Jobs | Строковая таблица статуса, попытки, аренды (lease) и параметров; ключ `job_id` |
| Outbox | Строковая таблица ожидающей постановки задания; стабильный прикладной `dispatch_id` |
| Ретранслятор Outbox / диспетчер | Внешнее приложение: получает запись об изменении Outbox и повторяемо отправляет сообщение в очередь SQS |
| Очередь SQS | Встроенная реализация SQS-совместимого протокола, доступная во всех поддерживаемых развертываниях YDB, с конкурирующими потребителями и visibility timeout |
| Обработчики | Внешние приложения: захват/получение, продление visibility, выполнение, фиксация результата и ack/delete |
| JobResults | Строковая таблица результата по `job_id` |
| IdempotencyKeys | Строковая таблица дедупликации попыток/операций |
| StatusOutbox | Строковая таблица статусных событий, атомарно записанных с результатом |
| Status events Topic | YDB Topic статусов; ретранслятор задает `producer_id = message_group_id = job_id` |
| DLQ | Сообщения после исчерпания политики повторов |

Очередь SQS и YDB Topics не взаимозаменяемы. SQS дает конкурирующих потребителей, visibility timeout, ack/delete, повторы и DLQ. Topic — партиционированный журнал pub/sub со смещением (offset) каждого именованного YDB Consumer. Для SQS не задаются Topic-поля `producer_id`/`message_group_id`: очередь присваивает сообщению `message_id`, а прикладная дедупликация использует стабильный `dispatch_id`/`job_id`; `deduplication_id` задается только если выбранный тип очереди явно поддерживает эту возможность.

Внутри границы YDB находятся строковые таблицы, потоки изменений CDC, Status events Topic, опциональная Coordination, очередь заданий SQS и DLQ. Producer/API, диспетчер/ретранслятор Outbox, ретранслятор статусов, обработчики и внешний сервис побочных эффектов — внешние приложения. Общей транзакции строковых таблиц и постановки в очередь SQS / подтверждения (ack) нет.

## Основной поток

1. Producer в одной ACID-транзакции обновляет `Business tables`, создает запись `Jobs` и соответствующую запись `Outbox`. Прямой постановки в очередь SQS нет, поэтому двойной записи нет.
2. CDC создает одну запись об изменении на зафиксированное изменение строки записи `Outbox`. Внешний диспетчер/ретранслятор может прочитать и обработать запись повторно, поэтому отправляет в очередь SQS стабильные прикладные `job_id` и `dispatch_id`; очередь возвращает собственный `message_id`.
3. Очередь SQS отдает сообщение одному из конкурирующих обработчиков: обработчик выполняет захват/получение, а очередь скрывает сообщение на visibility timeout.
4. Обработчик проверяет `IdempotencyKeys` и состояние `Jobs`. Для долгой операции он своевременно продлевает visibility, понимая, что аренда не является блокировкой внешнего побочного эффекта.
5. Обработчик выполняет внешний побочный эффект с `job_id` как ключом идемпотентности.
6. В одной ACID-транзакции обработчик обновляет `Jobs` и записывает `JobResults`, `IdempotencyKeys` и `StatusOutbox`.
7. Только после успешной фиксации обработчик отправляет в очередь SQS ack/delete с актуальным дескриптором получения. До фиксации ack запрещен; потерянный ack приводит к безопасной повторной доставке.
8. CDC создает одну запись об изменении на зафиксированное изменение строки `StatusOutbox`, после чего внешний ретранслятор статусов публикует статус в Status events Topic с `producer_id = message_group_id = job_id`. Чтение и обработка записи об изменении или сообщения Topic могут повторяться.
9. При временной ошибке обработчик не подтверждает сообщение: истечение таймаута видимости возвращает его в очередь SQS для повтора с экспоненциальной задержкой. После лимита повторная отправка (redrive) направляет сообщение в DLQ.

## Согласованность и надежность

Бизнес-изменение, `Jobs` и `Outbox` атомарны внутри первой транзакции YDB. Обновление `Jobs`, `JobResults`, `IdempotencyKeys` и `StatusOutbox` атомарно внутри транзакции результата. CDC создает одну запись об изменении на каждое зафиксированное изменение строки; ретранслятор и конечные подписчики могут читать и обрабатывать запись повторно. Постановка в очередь SQS, захват/получение, внешний побочный эффект и ack/delete не образуют одну транзакцию со строковыми таблицами, и обработка ровно один раз не обещается.

Одна очередь не обеспечивает внешний эффект ровно один раз. Обработчик может успешно вызвать внешний сервис и потерять visibility или упасть до фиксации/удаления; тогда другой обработчик получит то же сообщение. Внешняя операция обязана быть идемпотентной по стабильному ключу или поддерживать запрос ранее полученного результата. Для неидемпотентного API нужен прикладной протокол сверки и возможность ручного разрешения.

Coordination при дополнительном назначении лидера диспетчера не заменяет ACID и обычно не нужна для эксклюзивности обработки: эту роль выполняет SQS visibility. Если Coordination все же применяется, необходимы сессии и fencing.

## Масштабирование и ключи партиционирования

Исходный `job_id` остается в PK таблиц `Jobs`, `JobResults` и `IdempotencyKeys`. Если нужно хеш-шардирование, хеш используется только как префикс шарда: `(hash(job_id) % N, job_id, ...)`. Для выборки Outbox по состоянию используют bucket и префикс шарда с исходным `job_id` в PK, а не одну монотонную временную метку. Диспетчер обрабатывает шарды параллельно.

Количество обработчиков масштабируется по глубине очереди, возрасту старейшего сообщения и длительности обработки. Visibility timeout должен превышать типичный интервал между продлениями по heartbeat, но не быть настолько большим, чтобы затягивать восстановление. Для Status events Topic ретранслятор задает `producer_id = message_group_id = job_id`; порядок статусов одного задания сохраняется внутри `producer_id`. Подписчики используют именованные YDB Consumers.

## Отказы и восстановление

Если ретранслятор упал до отправки, чтение записи CDC будет повторено; если после отправки, возможен дубликат сообщения SQS. CDC создает одну запись об изменении на зафиксированное изменение строки, но не гарантирует однократную обработку. Если обработчик упал до побочного эффекта, сообщение вернется по истечении таймаута видимости. Если после побочного эффекта, повтор проверяет внешний ключ идемпотентности и локальные `IdempotencyKeys`. Если фиксация прошла, а ack/delete потерялся, повтор обнаружит сохраненный результат и снова подтвердит сообщение.

Повтор выполняется с экспоненциальной задержкой и случайным разбросом. Постоянные, невалидные и исчерпавшие попытки сообщения перемещаются в DLQ. Оператор проверяет `Jobs`, `JobResults` и фактическое состояние внешней системы, затем переотправляет, помечает завершенным либо отменяет задание.

## Ограничения и антипаттерны

- Писать бизнес-данные и напрямую выполнять постановку в очередь SQS двумя несвязанными операциями вместо транзакционного `Outbox` и CDC/ретранслятора.
- Считать visibility timeout взаимным исключением для внешнего побочного эффекта.
- Обещать доставку ровно один раз только потому, что очередь удаляет успешно обработанное сообщение.
- Использовать случайный ключ идемпотентности при каждой попытке.
- Удалять сообщение до фиксации результата.
- Публиковать статус напрямую из обработчика вместо атомарной записи `StatusOutbox`.
- Делать бесконечный повтор без экспоненциальной задержки, лимита и DLQ.
- Использовать Topic как очередь конкурирующих потребителей либо очередь SQS как журнал pub/sub.
- Считать Coordination заменой ACID-транзакции.
